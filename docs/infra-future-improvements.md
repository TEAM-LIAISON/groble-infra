## 🔴 Urgent

### Urgent-1. ElastiCache replica 도입 (단일 노드 → 복제 그룹) {#urgent-1}

**이번에 하지 않은 이유**: 비용($15/월)을 이유로 단일 노드로 시작하기로 결정(계획서 §2.3).

**그런데 이건 단순한 캐시 HA 문제가 아니다.**

애플리케이션 코드 확인 결과, Prod Redis에 들어있는 것의 대부분은 캐시가 아니라 **결제 경로의 트랜잭션 상태**다:

| 키 | 역할 | Redis가 유일한 권위 소스인가 |
|---|---|---|
| `checkout:idempotency:*` | 결제 멱등성 키 | **예** |
| `stock:reserved:*` | 재고 예약 카운터 (초과 시 즉시 실패) | **예** |
| `checkout:session:*` | 체크아웃 세션 | 예 |
| `user:cache:*` | JWT 사용자 캐시 | 아니오 (DB에서 회복) |

**단일 노드 유실의 결과는 "캐시 미스"가 아니라 다음이다:**
- 멱등성 키 소실 → **중복 결제 방어 무력화**
- 재고 예약 소실 → **재고 초과 판매**
- 진행 중 체크아웃 실패

**그리고 이 창은 우발적이지 않다.** ElastiCache 단일 노드는 **AWS 유지보수 시 예정된 일정으로** 다운된다. "무중단 하드웨어 교체"를 목표로 시작한 프로젝트가 데이터 계층에 계획된 다운타임을 남기는 셈이라, 목표와 정면으로 모순된다.

**해결안**
```hcl
# ElastiCache replication group
automatic_failover_enabled = true
multi_az_enabled           = false   # 단일 AZ 결정과 충돌 없음
# primary + replica 1, 둘 다 ap-northeast-2c
```
- replica를 같은 AZ(2c)에 두면 cross-AZ 비용도 없고 단일 AZ 결정도 뒤집지 않는다.
- 노드 장애·유지보수 시 수십 초 내 자동 failover, 데이터 유지.
- **실행 비용은 이미 낮춰 두었다**: 계획서 v3 §2.3에 따라 단일 노드도 `aws_elasticache_replication_group` 리소스로 생성하므로, replica 추가는 `num_cache_clusters = 2` + `automatic_failover_enabled = true`의 **온라인 변경**이다. 엔드포인트가 유지되어 앱 재배포도 상태 유실도 없다. (`aws_elasticache_cluster`로 만들었다면 리소스 재생성 = 결제 상태 2차 유실 이벤트였다.)

**비용**: +$15/월 (~$15 → ~$30). Reserved Node 적용 시 ~$20.

**트리거**: 즉시 검토. 결제 거래량이 늘수록 미루는 비용이 커진다.

**한시 조치 (replica 도입 전까지 반드시 유지)**
- ElastiCache 유지보수 창을 **트래픽 최저 시간대로 명시 지정** (기본값은 무작위 배정)
- 자동 스냅샷 활성화
- Redis 상실 시 앱 거동을 **게임데이로 실측** (계획서 §4 To-Do 5)

## 🟠 High

### High-1. 멱등성·재고 예약의 Redis 의존 해소 {#high-1}

**배경**: Urgent-1은 인프라로 위험을 줄이지만, **구조적으로는 여전히 인메모리 저장소가 금전 정합성의 권위 소스**다. Redis 복제도 비동기라 failover 시 in-flight 쓰기 유실 가능성이 남는다.

**해결안**: `checkout:idempotency:*`와 `stock:reserved:*`를 MySQL로 이전한다.
- 멱등성: 유니크 제약 + 트랜잭션
- 재고 예약: 행 잠금 또는 조건부 UPDATE, TTL은 만료 컬럼 + 정리 배치

**이번에 하지 않은 이유**: 애플리케이션의 동시성 설계를 다시 검증해야 하는 큰 작업이라, 인프라 마이그레이션 일정에 얹으면 전체가 지연된다.

**대가**: DB 쓰기 부하 증가 (재고 예약은 쓰기가 잦다). RDS 인스턴스 크기 재검토가 따라올 수 있다.

**트리거**: 결제 관련 정합성 사고가 1회라도 발생하면 즉시. 또는 거래량이 현재의 수 배로 늘어날 때.

### High-2. N+1 노드 확보 (Prod desired 2 → 3) {#high-2}

**배경**: 현재 구조는 노드 2대 × ENI 2슬롯 = 4슬롯이다. 노드 1대를 잃으면 슬롯이 2/2로 꽉 차서 **배포가 불가능해진다** (계획서 §2.1의 "알려진 제약").

장애 대응 중에 핫픽스를 낼 수 없다는 뜻이라, 가장 필요한 순간에 손이 묶인다.

**해결안**: ASG `desired`를 3으로. ASG이므로 **값 하나만 바꾸면 된다** — pet 구조에서는 불가능했던 유연성이다.

**비용**: t3.medium 1대 = 약 $38/월.
→ **Compute Savings Plan(1년 no-upfront) 적용 시 3대 총액이 약 $82/월**로, 현재 2대 온디맨드($76)와 거의 같아진다. 비용 문제를 노드 수가 아니라 구매 방식에서 푸는 것이 효율적이다.

**대안**: 헤드룸 노드만 Spot으로 (mixed instances policy, +$11/월). 중단되어도 원래의 2노드 상태로 돌아갈 뿐이라 손실이 제한적이다.

**트리거**: 노드 장애 중 배포가 필요했던 상황이 1회 발생하면. 또는 Savings Plan 도입 시 함께.

### High-3. Prometheus 장기 보관 실구현 {#high-3}

**배경 — 현재 인식과 사실이 다르다.**

CLAUDE.md는 *"Prometheus: 로컬 15일, S3 장기 저장(90일)"* 이라고 기술하고 있고 S3 버킷과 IAM 권한도 만들어져 있다. **그러나 실제로는 사용되지 않는다** — 바닐라 Prometheus는 S3에 직접 쓸 수 없고, 코드에 Thanos·Mimir 같은 구성요소가 없다.

**현재 Prometheus 데이터는 로컬 15일이 전부이며, 노드 교체 시 그마저도 사라진다.**

**선택지**

| 방식 | 특징 | 비용 |
|---|---|---|
| Thanos sidecar + S3 | 표준적. 구성요소 추가(sidecar, store gateway, querier) | 인스턴스 자원 + S3 |
| Grafana Mimir | 통합도가 높지만 운영 부담이 큼 | 자원 + S3 |
| **AWS Managed Prometheus (AMP)** | 관리형. `remote_write`만 설정 | 수집 지표량에 비례 |
| 현행 유지 (15일) | 추가 작업 없음 | $0 |

**이번에 하지 않은 이유**: 관측 스택 구조 변경이라 마이그레이션과 병행하면 문제 원인 규명이 어려워진다.

**트리거**: 15일을 넘는 기간의 지표 비교가 필요해질 때 (용량 계획, 계절성 분석, 장기 성능 회귀 추적).

**즉시 할 일**: CLAUDE.md의 서술을 사실에 맞게 정정한다. 잘못된 문서는 "백업이 있다"고 믿게 만들어 더 위험하다.

### High-4. Prod RDS 메모리 압박 해소 {#high-4}

**상태**: 추정이 아니라 **실측으로 확인된 문제다.** Phase 1의 알람을 붙이자마자 드러났다.

| 지표 | 실측값 | 판단 |
|---|---|---|
| `FreeableMemory` | 21~62 MiB (평균 42) / 총 1 GiB | 만성 부족 |
| `SwapUsage` | 400~482 MiB, 7일간 안정된 고원 | 절반 가까이를 디스크로 밀어냄 |
| `CPUUtilization` | 4.7~5.0% | 놀고 있음 |
| `CPUCreditBalance` | 288 (최대치) | 버스트를 쓰지도 않음 |
| `DatabaseConnections` | 14개 | 여유 |

**병목은 메모리 하나다.** CPU·크레딧·커넥션·스토리지가 모두 넉넉한데 메모리만 포화 상태다.

**원인**: 파라미터 그룹의 `innodb_buffer_pool_size`가 엔진 기본 공식
`{DBInstanceClassMemory*3/4}` ≈ **768 MiB**로 설정되어 있다. 총 1 GiB에서 이만큼을 버퍼 풀이
가져가면 mysqld 오버헤드와 OS에 약 256 MiB만 남아 스왑으로 밀린다.
이 공식은 메모리가 넉넉한 인스턴스를 전제하며, `db.t3.micro`에는 과하다.

**RDS 스왑은 곧 디스크 I/O다.** gp2 볼륨이라 지연으로 직결된다.
CLAUDE.md에 기록된 "RDS는 2c / Prod EC2는 2a라 모든 쿼리가 cross-AZ"와 겹치면
DB 응답 지연의 원인이 두 겹으로 쌓여 있는 셈이다.

**선택지**

| | 방법 | 비용 | 재부팅 | 트레이드오프 |
|---|---|---|---|---|
| A | 버퍼 풀을 `{DBInstanceClassMemory*1/2}`(≈512 MiB)로 축소 | $0 | 필요 | 캐시가 줄어드는 대신 스왑이 줄어든다. **순효과는 개선일 가능성이 높지만 확신은 아니다** — 워크로드의 작업 세트 크기를 모른다 |
| B | `db.t3.micro` → `db.t3.small` (1 → 2 GiB) | 약 **+$18/월** | 필요 | 근본 해결 |

둘 다 **프로덕션 DB 재부팅**이 필요하다(단일 AZ이므로 수십 초~수 분 순단). 유지보수 창이 필요하다.

**트리거**: **[Phase 6](./runbook/phase-06-elasticache.md) 진입 전에 결정한다.**
Redis를 ElastiCache로 빼면 결제 경로가 DB에 더 의존하게 된다. 그 전에 이 상태를 해소하거나,
최소한 수용 여부를 명시적으로 결정해야 한다.

`groble-prod-rds-swap` 알람(임계치 600 MiB)이 울리면 결정을 더 미룰 수 없다는 신호다.

**함께 발견한 것 — `max_connections = 200`**

파라미터 그룹에 `max_connections`가 **200으로 명시 설정**되어 있다(엔진 기본 공식값은 약 85).
현재 사용량이 14개라 무해하지만, **커넥션이 실제로 200개까지 열리면 이 인스턴스의 메모리는 버티지 못한다.**
앱 커넥션 풀 상한과 이 값이 정합한지 확인이 필요하다. 위 A/B 결정 시 함께 검토할 것.

## 🟡 Medium

### Medium-1. 모니터링 노드 데이터의 EBS 볼륨 분리 {#medium-1}

**배경**: Grafana는 as-code로 재현 가능해졌지만(계획서 §2.4), Prometheus 로컬 TSDB 15일치는 노드 교체 시 사라진다.

**해결안**: `/opt`를 별도 EBS 볼륨으로 분리하고 노드 교체 시 재연결. Terraform `aws_volume_attachment`로 관리.

**이번에 하지 않은 이유**: 시계열 유실은 **회복 가능한 손실**이다(로그는 S3에 있고 지표는 다시 쌓인다). 반면 대시보드 유실은 사람의 작업 시간을 다시 쓰게 만들므로 우선순위가 높았고, 그쪽(as-code)을 먼저 처리했다.

**비용**: 30GB gp3 ≈ $3/월.

**트리거**: 모니터링 노드의 AMI 패치나 타입 변경이 예정되었을 때. 또는 High-3(장기 보관)을 도입하면 필요성이 줄어든다.

### Medium-2. 피처 플래그 (dark launch) {#medium-2}

**배경**: rolling 전환으로 **테스트 리스너(9443) 기반 사전검증을 잃었고, 롤백이 분 단위**가 되었다(계획서 §2.6 트레이드오프). 계획서 §3-5는 이를 Dev promote 게이트로 갈음했지만, 플래그는 여기서 더 나아간다:

- **배포와 릴리스를 분리**한다 — 코드는 나가되 기능은 꺼진 상태
- 문제 발생 시 **재배포 없이 즉시 플래그 오프** → 롤링의 느린 롤백을 상쇄

**이번에 하지 않은 이유**: 애플리케이션 작업량이 크고, 인프라 마이그레이션의 선결 조건은 아니다.

**트리거**: 롤백 지연이 실제로 문제가 된 사례가 나오거나, 위험도 높은 기능 출시가 예정되었을 때.

### Medium-3. 가중 타깃그룹 기반 카나리 배포 {#medium-3}

**배경**: 마이그레이션 Phase 5에서 리스너 가중치 전환 방식을 검토했으나, 그 단계에서 옮기는 것은 **같은 애플리케이션 버전**이라 점진 전환으로 얻는 정보가 적어 즉시 스왑을 택했다.

**그러나 일상 배포에서는 값어치가 다르다.** ALB 리스너 규칙의 `forward` 액션에 두 타깃그룹의 가중치를 두고 10% → 50% → 100%로 옮기면, 신 버전을 소량 트래픽으로 먼저 검증할 수 있다.

**전제**: 계획서 §3-1(expand/contract)이 지켜져야 한다 — 카나리 중에는 구/신 버전이 확실히 공존한다.

**비용**: $0 (이미 있는 ALB·TG 활용). CI 파이프라인 작업이 필요하다.

**트리거**: rolling 배포에서 사고가 1회 발생하면. 또는 Medium-2(피처 플래그)와 함께 릴리스 안전성을 체계화할 때.

---

### Medium-4. VPC Interface Endpoint 도입 검토 {#medium-4}

**배경**: 이번에 **S3 Gateway Endpoint(무료)** 는 도입했다. ECR 이미지 레이어가 S3에서 오므로 NAT 데이터 요금의 상당 부분이 이것으로 제거된다.

남은 후보는 Interface Endpoint(`ecr.api`, `ecr.dkr`, `ssm`, `ssmmessages`, `ec2messages`, `logs`)인데, 이쪽은 **시간당 과금 + 데이터 처리 요금**이 있어 무조건 이득이 아니다.

**판단 방법**: NAT Gateway의 실제 데이터 처리량(CloudWatch `BytesOutToDestination` 등)을 1개월 관측한 뒤, 엔드포인트 고정비와 비교한다.

**트리거**: NAT Gateway 데이터 요금이 월 $10을 넘어설 때.

### Medium-5. 관측 평면의 HA (모니터링 노드 ASG화) {#medium-5}

**배경**: 계획서 §0에서 모니터링 노드의 무중단 교체를 **명시적 비목표**로 두고 pet으로 남겼다. 이유는 관측 단절이 서비스 가용성에 영향을 주지 않기 때문이고, 가용성 직결 항목(High-2의 N+1 노드)조차 비용으로 미룬 상황에서 관측 HA를 먼저 사는 것은 우선순위가 맞지 않았다.

**해결안**: 모니터링 노드를 ASG(size 1)로 만들고, 앱이 바라보는 OTLP 엔드포인트를 **내부 NLB**로 안정화한다.
- 안정화가 필요한 지점은 **앱 → otelcol 하나뿐**이다. otelcol·Prometheus·Loki·Grafana는 같은 노드에서 host mode로 돌며 `localhost`로 통신한다.

**비용**: 내부 NLB ≈ $16/월 + LCU.

**대안 (비용 $0)**: otelcol을 awsvpc + Cloud Map으로 등록. 단 같은 노드 컴포넌트 간 `localhost` 통신이 깨져 잘 도는 구성을 오히려 복잡하게 만든다 — 권하지 않는다.

**트리거**: 모니터링 노드 장애로 인한 관측 단절이 실제 장애 대응을 방해한 사례가 발생했을 때.

## 🔵 Low / 조건부

### Low-1. ENI trunking (`awsvpcTrunking`) {#low-1}

**배경**: awsvpc 모드에서 t3 계열은 ENI 3개(primary 1 + secondary 2)라 **노드당 태스크가 2개로 제한**된다. trunking을 켜면 branch ENI로 밀도를 크게 올릴 수 있다.

**이번에 하지 않은 이유 — 지금 켜도 이득이 없다.**

t3.medium(4GiB)에서 API 태스크가 ~1200MB를 쓰므로 **메모리가 먼저 2태스크에서 막는다.** ENI를 풀어도 실질 밀도는 그대로다. 이득을 실현하려면 t3.large 이상이 필요한데, 그러면 3× t3.medium보다 비싸진다.

| 구성 | 슬롯 (ENI / 메모리) | 월 비용 |
|---|---|---|
| 현행 2× t3.medium | 4 / 4 | ~$76 |
| 3× t3.medium (High-2) | 6 / 6 | ~$114 |
| trunking + 2× t3.large | ~20 / 6 | ~$152 |

**트리거**: ① 태스크당 메모리가 크게 낮아지거나, ② 노드를 적고 크게 가져가는 구조로 전환하거나, ③ 한 노드에 여러 종류의 서비스를 밀도 있게 올릴 때.

**전제**: ECS-optimized AMI가 사실상 필요한데, 이번에 이미 전환했으므로 **도입 시점의 장벽은 낮아진 상태다.**

---

### Low-2. 멀티 AZ / AZ 장애 생존 {#low-2}

**배경**: 계획서 §0의 명시적 비목표. "무중단 하드웨어 교체"와 "AZ 장애 생존"은 다른 목표이며, 전자는 단일 AZ로 충분하다.

**도입 시 필요한 것 (부분 도입은 의미가 적다)**
- ASG를 2 AZ에 배치
- RDS `multi_az = true` (비용 약 2배)
- ElastiCache Multi-AZ + 자동 failover
- NAT Gateway 2개
- cross-AZ 데이터 전송 비용 상시 발생

> **주의**: 컴퓨트만 2 AZ로 펼치고 데이터 계층을 단일 AZ에 두면, AZ 장애 시 어차피 전체가 죽으면서 **평상시 cross-AZ 비용과 지연 이중봉만 얻는다.** 하려면 데이터 계층까지 함께 가야 한다.

**트리거**: 사업적으로 가용성 SLA를 약속해야 할 때. 또는 AZ 장애로 실제 매출 손실을 겪었을 때.

**참고**: 이번 프로젝트에서 단일 AZ의 실질 리스크로 식별한 **`InsufficientInstanceCapacity`** 는 mixed instances policy(t3/t3a)로 이미 완화했다. 멀티 AZ의 동기 중 하나는 이미 해소된 상태다.

---

### Low-3. 동적 오토스케일링 {#low-3}

**배경**: 계획서 §0의 비목표. 고정 크기 ASG로 시작하고, 트래픽 변동이 실측으로 확인되면 도입한다.

**도입 전에 확보해야 할 것 — 지금 이 데이터가 없다.**
계획서 전체에 트래픽 수치가 하나도 없고, 2대가 충분하다는 근거가 메모리 실측뿐이다. 다음을 먼저 상시 관측 대상으로 지정한다:
- ALB `RequestCountPerTarget`, `TargetResponseTime` p99
- 태스크 CPU/메모리 사용률
- 피크 시간대와 피크/평균 비율

**주의**: ECS 서비스 오토스케일링과 ASG 스케일링을 **함께** 설계해야 한다. 태스크만 늘려도 노드 슬롯(ENI 2개)이 없으면 배치되지 않는다. Capacity Provider의 managed scaling을 켜는 것이 정공법이다.

**트리거**: 피크/평균 비율이 2배를 넘고, 그 패턴이 예측 가능해질 때.

---

### Low-4. Dev 전용 모니터링 검증 베드 {#low-4}

**배경**: 계획서 v1은 Prod/Dev 모니터링 분리를 제안했으나 v2에서 철회했다(통합 스택 + config baking CI 검증). 스택 두 벌은 대시보드·알람·설정을 이중 관리하게 만들어 온보딩 부담을 늘린다.

**남은 리스크**: 모니터링 스택 업그레이드 시 **Prod 관측이 직접 위험에 노출**된다. CI의 설정 검증은 문법까지이고, 메이저 업그레이드로 쿼리·대시보드가 깨지는 것은 런타임에서만 드러난다.

**현재 대응**: 메이저 업그레이드 시 **일회성 임시 노드**를 띄워 검증하고 내린다. 상시 병렬 스택보다 경제적이다.

**비용(상시 도입 시)**: 스택 합계가 ~2048MB라 t3.small에 안 들어간다 → t3.medium 필요, 약 $38/월. 축소판으로 맞추면 "Prod와 다른 구성"이 되어 검증 가치가 떨어지는 딜레마가 있다.

**트리거**: 모니터링 스택 업그레이드로 Prod 관측이 중단된 사고가 발생했을 때.

---

### Low-5. Dev를 Prod와 동일한 롤링 전략으로 (t3.small → t3.medium) {#low-5}

**배경**: Dev는 t3.small(2GiB)이라 노드당 API 태스크가 1개뿐이고, 따라서 Prod의 surge 방식(`100 / 150`)을 쓸 수 없다. 축소 우선 방식(`50 / 100`)으로 운용하기로 했다(계획서 §2.1).

**이번에 하지 않은 이유**: Dev를 t3.medium 2대로 올리면 Prod와 동일 전략을 쓸 수 있지만 월 $38가 추가된다. 같은 예산이라면 Urgent-1(ElastiCache replica)이나 High-2(Prod N+1 노드)에 쓰는 편이 낫다고 판단했다.

**남는 공백**: Dev promote 게이트에서 **surge 배치가 검증되지 않는다** — Prod에서 3번째 태스크가 슬롯에 들어가는 동작, 그 시점의 노드 메모리·ENI 압력. 버전 공존·드레이닝·readiness·서킷 브레이커는 축소 우선 방식에서도 그대로 검증된다.

**현재 대응**: surge 배치는 Prod 전환 시 instance refresh 리허설과 노드 강제 종료 테스트에서 실측한다(런북 Phase 7).

**트리거**: surge 배치와 관련된 배포 사고(피크 태스크 배치 실패, 노드 메모리 압박으로 인한 OOM 등)가 Prod에서 발생했을 때. 또는 Dev의 실사용 메모리가 900MiB를 넘어 t3.small이 한계에 도달했을 때.

## ⚪ 상시 검토

### Cost-1. Savings Plan / Reserved Node {#cost-1}

이번 프로젝트에서 **비용을 이유로 미룬 결정이 여럿 있다** (High-2의 N+1 노드, Urgent-1의 replica). 그런데 이 비용들은 **구매 방식으로 상당 부분 흡수된다.**

| 대상 | 방식 | 절감 |
|---|---|---|
| EC2 (ASG 노드) | Compute Savings Plan 1년 no-upfront | 약 28~30% |
| ElastiCache | Reserved Node 1년 no-upfront | 약 30~35% |
| RDS (Prod/Dev) | Reserved Instance 1년 no-upfront | 약 30~40% |

**예시**: N+1 노드(3× t3.medium)를 Savings Plan으로 사면 월 ~$82로, 현재 2대 온디맨드($76)와 거의 같다. 즉 **가용성 개선을 사실상 비용 중립으로 얻을 수 있다.**

**트리거**: 이번 마이그레이션이 완료되어 인스턴스 타입·수량이 안정화된 직후. 구성이 바뀌는 중에 커밋하면 낭비가 생기므로 **마이그레이션 완료 후**가 적기다.

## 이 문서의 운영

- 항목이 해소되면 **삭제하지 말고 "완료" 표시와 함께 남긴다.** 왜 그런 결정을 했는지의 기록이 다음 판단에 쓰인다.
- 새로 식별된 항목은 **트리거를 반드시 함께 적는다.** 트리거 없는 항목은 우선순위 경쟁에서 밀려 영구히 남는다.
- 분기마다 우선순위를 재검토한다 — 특히 🔴 Urgent 항목이 오래 남아 있으면 그 자체가 신호다.
