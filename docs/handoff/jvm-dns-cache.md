## 요청 요약

**JVM 의 `networkaddress.cache.ttl` 현재 값을 알려주시고, 60초 이하로 설정해 주세요.**

확인이 아니라 **설정 변경 요청**입니다. 값이 사실상 무기한이라는 것은 이미 관측됐습니다.

---

## 왜 필요한가 — 두 가지가 같은 원인입니다

### 1. 이미 한 번 사고가 났습니다 (2026-08-29)

RDS 8.4 스위치오버 때 **약 7~8분간 결제·저장 등 쓰기가 실패**했습니다.

- DNS 는 정상이었습니다 — `groble-prod-mysql` 이 신규 인스턴스를 가리키고 있었습니다
- 그런데 앱 커넥션 10개가 **구 DB 로 재연결**됐습니다. **JVM 이 옛 IP 를 캐시**한 것입니다
- 헬스체크는 200 이었습니다 (조회는 구 DB 에서도 되므로 이상을 감지하지 못했습니다)
- **재배포를 하고서야 해소**됐습니다 — 새 JVM 이 뜨면서 DNS 를 다시 조회했습니다

TTL 이 짧았다면 최대 60초 만에 스스로 회복됐을 사건입니다.

### 2. 모니터링 노드 교체가 이것 하나에 막혀 있습니다

PR #882·#883 로 전송 주소를 `otel.internal.groble.im` 으로 바꿔 주신 것이
**바로 이 구조를 위한 것이었습니다.**

```
지금  otel.internal.groble.im → 10.0.1.193 (구 노드)
전환  레코드 값만 10.0.12.100 (신 노드) 으로 변경  → 60초 내 이동, 앱 재배포 없음
```

**그런데 JVM 이 DNS 를 무기한 캐시하면 이 구조가 동작하지 않습니다.** 레코드를 바꿔도
앱이 옛 노드를 계속 붙잡아, 결국 노드를 교체할 때마다 앱을 재배포해야 합니다 —
주소를 이름으로 뺀 의미가 사라집니다.

인프라 쪽 준비는 모두 끝났고(신 노드 기동 완료), **이 항목이 남은 유일한 차단 조건입니다.**

---

## 여쭙는 것

1. **`networkaddress.cache.ttl` 의 현재 값**은 무엇인가요?
   그리고 **60초 이하로 설정해 주실 수 있나요?**

   설정 위치는 둘 중 편한 쪽이면 됩니다:
   - `$JAVA_HOME/conf/security/java.security` 의 `networkaddress.cache.ttl=60`
   - JVM 옵션 `-Dsun.net.inetaddr.ttl=60`

   > 참고: 값을 지정하지 않으면 SecurityManager 유무에 따라 무기한(-1)이 될 수 있습니다.
   > 8/29 사건의 거동이 그와 일치합니다.

2. **OTLP exporter 가 쓰는 HTTP 클라이언트가 커넥션 풀에서 IP 를 고정하지는 않나요?**

   DNS TTL 이 짧아도 커넥션을 계속 재사용하면 옛 노드로 계속 보내게 됩니다.
   OpenTelemetry Java 기본 exporter 를 쓰시는지, 커넥션 유지 관련 별도 설정이 있는지만
   알려 주셔도 됩니다.

---

## 일정

급하지는 않지만 **모니터링 노드 교체가 여기서 멈춰 있습니다.** 1번만 먼저 주셔도 됩니다.

1번 설정은 **8/29 같은 DB 전환 사고의 재발도 함께 막습니다** — RDS 엔드포인트든
모니터링 노드든, DNS 로 가리키는 대상이 바뀔 때 앱이 스스로 따라오게 됩니다.
