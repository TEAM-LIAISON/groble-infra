## 결론 먼저

**제보해 주신 3건 중 2건은 고쳤고, 1건은 고칠 수 없습니다.**
그리고 **제보 목록에 없던 4번째 차이를 하나 더 찾아서 같이 고쳤습니다.**

그린은 **재부팅까지 마쳐 이미 반영된 상태**입니다. 접속 정보는 그대로입니다.

> **버퍼풀이 블루와 같아졌으니, 먼저 재보신 실행계획·응답시간이 전환 후와 어긋나지 않습니다.**
> 이전에 측정하신 값이 있다면 **다시 한 번 봐 주시길** 부탁드립니다. (§5)

## 1. 인스턴스 클래스는 문제가 아니었습니다

먼저 물어보신 것부터 답합니다. **양쪽 모두 `db.t3.micro` 로 동일합니다.**

| | 인스턴스 | 클래스 | 엔진 |
|---|---|---|---|
| 블루 | `groble-prod-mysql` | `db.t3.micro` | 8.0.45 |
| 그린 | `groble-prod-mysql-green-ftzmon` | `db.t3.micro` | 8.4.11 |

**원인은 AWS 가 8.0 과 8.4 에 서로 다른 기본값을 주기 때문입니다.**

| 파라미터 | 8.0 기본값 | 8.4 기본값 |
|---|---|---|
| `innodb_dedicated_server` | 없음 (= 꺼짐) | **켜짐** |
| `innodb_buffer_pool_size` | 메모리의 3/4 | **없음** |
| `innodb_redo_log_capacity` | 2 GiB | **없음** |
| `log_output` | `TABLE` | **없음** |

8.4 부터 AWS 는 크기 기본값을 없애고 **MySQL 이 감지한 메모리로 자동 계산**하게 바꿨습니다.
그런데 1 GiB 인스턴스에서는 자동 계산이 **"1GB 미만" 구간의 최솟값**을 잡습니다.
말씀하신 "128MB 는 좀 이상하다" 는 감각이 정확했습니다 — 최솟값이 맞습니다.

**저희 쪽 실수도 겹쳐 있습니다.** 8.4 파라미터 그룹을 만들 때 `innodb_buffer_pool_size` 를
일부러 넣지 않았습니다. 8.0 에서 그 값이 기본값과 똑같아 "넣으나 마나" 라고 판단했는데,
8.0 기준으로만 맞는 이야기였습니다.

## 2. 수정 결과

| 파라미터 | 블루 | 그린 (수정 전) | 그린 (수정 후) |
|---|---|---|---|
| `innodb_buffer_pool_size` | 256 MiB | **128 MiB** | **256 MiB** ✅ |
| `innodb_redo_log_capacity` | 2048 MiB | **1024 MiB** | **2048 MiB** ✅ |
| `innodb_dedicated_server` | 0 | 1 | **0** ✅ |
| `log_output` | `TABLE` | `FILE` | **`TABLE`** ✅ |

**`innodb_redo_log_capacity` 가 제보 목록에 없던 4번째입니다.** 같은 원인(자동 계산)의 파생이라
버퍼풀만 고치면 이쪽이 남았을 겁니다.

`innodb_dedicated_server` 는 켜져 있으면 MySQL 이 크기를 자동으로 정하고 **직접 지정한 값을 무시**합니다.
그래서 이걸 먼저 꺼야 나머지가 적용됩니다. 재시작이 필요한 항목이라 **그린을 재부팅**했고,
재부팅 후 복제는 스스로 재개했으며 데이터도 계속 일치합니다 (511,385행, 양쪽 동일).

### 왜 8.4 자동값(128MB)을 그냥 두지 않았나

**버전 업그레이드는 다른 조건을 똑같이 두고 해야** 문제가 생겼을 때 원인을 가릴 수 있습니다.
버퍼풀이 반토막인 채로 넘어가면, 전환 후 느려졌을 때 그게 8.4 때문인지 캐시가 줄어서인지
구분할 수 없습니다. 버퍼풀 조정이 필요하다면 **전환이 끝난 뒤 측정해서 따로** 하는 게 맞습니다.

## 3. 고칠 수 없는 것 1건 — `log_error_suppression_list`

블루의 `MY-013360` 은 **저희가 설정한 값이 아니라 AWS 가 내부적으로 넣은 것**입니다.
확인해 보니 이 항목은 **RDS 가 조정 가능한 파라미터로 아예 제공하지 않습니다**
(8.0·8.4 양쪽 파라미터 그룹 어디에도 없습니다). 그래서 그린에 똑같이 넣을 방법이 없습니다.

- `MY-013360` 은 **`mysql_native_password` 가 구식이라는 경고**입니다
- 8.4 에서는 이 경고가 **에러 로그에 남게 됩니다**
- **기능에는 영향이 없습니다.** 로그에 한 줄 더 남는 것뿐입니다

> 참고로 이 인증 방식은 RDS 8.4 에서도 그대로 동작합니다(AWS 가 켠 채 고정해 두었습니다).
> 다만 MySQL 이 다음 메이저 버전에서 제거할 예정이라, **이번 전환과 분리해 별건으로**
> `caching_sha2_password` 로 옮길 계획입니다.

## 4. 전체 변수를 통째로 비교했습니다 — 두 가지 알려드립니다

제보 주신 김에 **글로벌 변수 606개 전수 비교**를 돌렸습니다. 위 4건 외의 실질 차이는
전부 MySQL 8.4 자체의 기본값 변경이었습니다. 그중 **성능 검증에 영향이 있을 두 가지**입니다.

### ① `optimizer_switch` — 안심하셔도 됩니다

**기존 플래그 값이 블루와 전부 동일합니다.** 유일한 차이는 8.4 에서 새로 생긴
`hash_set_operations=on` 하나뿐입니다.

**즉 기존 쿼리의 실행계획이 옵티마이저 설정 차이 때문에 바뀌지는 않습니다.**
계획이 달라진 게 보이면 그건 설정이 아니라 8.4 옵티마이저 자체의 변화입니다.

### ② `innodb_io_capacity` — 성능 측정하실 때 감안해 주세요

| | 블루 | 그린 |
|---|---|---|
| `innodb_io_capacity` | 200 | **10000** |
| `innodb_io_capacity_max` | 2000 | **20000** |

8.4 가 기본값을 크게 올렸습니다. 그런데 **저희 스토리지(gp2 20GB)의 기본 성능은 60 IOPS** 라
실제와 크게 어긋납니다. MySQL 이 "디스크가 빠르다" 고 믿고 과하게 쓰기를 몰아치면
버스트 성능을 미리 써버릴 수 있습니다.

**이번에는 일부러 손대지 않았습니다.** 8.4 기본값을 존중하는 게 맞고, 지금 바꾸면
위에서 말씀드린 "다른 조건을 똑같이" 원칙이 깨집니다. 대신 **전환 후 디스크 버스트 잔량을
관찰**하기로 했고, 문제가 보이면 그때 측정해서 조정하겠습니다.

성능 측정 중 **디스크 쪽이 이상하게 느리거나 반대로 이상하게 빠르면** 이 값 때문일 수 있습니다.

## 5. 부탁드리는 것

**그린 재검증 한 번만 더 부탁드립니다.** 버퍼풀이 블루와 같아졌으므로, 이전 측정값이
있다면 지금 값과 달라졌을 수 있습니다.

```
1. 실행계획 — 이전과 동일한가
2. 응답시간 — 이전 측정과 차이가 있는가 (버퍼풀 128 → 256 MiB)
3. 그 외 눈에 띄는 파라미터 차이가 더 있는가
```

접속 방법은 [이전에 드린 안내](./rds-84-green-access.md) 그대로입니다. 엔드포인트도 동일합니다.

**전수 비교를 해 주신 덕분에 찾았습니다.** 이 상태로 전환했으면 캐시가 절반인 채로
운영에 나갔을 겁니다. 감사합니다.
