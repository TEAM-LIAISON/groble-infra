## 1. 왜 올려야 하나

**2026년 8월 1일부터 운영 DB에 없던 과금이 붙기 시작했습니다.**

MySQL 8.0의 표준 지원이 7월 31일로 끝나면서, 8월 1일 00시부터 **RDS 확장 지원(Extended
Support)** 요금이 자동으로 부과되고 있습니다. 실측입니다.

| | 7/1~7/25 | 8/1~8/25 |
|---|---:|---:|
| 확장 지원 | — | **$143.28** |
| 인스턴스 + 스토리지 | $17.71 | $17.63 |
| **합계** | **$17.71** | **$160.91** |

**트래픽이나 사용량은 그대로인데 9.1배가 됐습니다.** 증가분 전액이 확장 지원 한 항목입니다.
월 환산 $178.56이고, 방치하면 내년에 요율이 한 번 더 오릅니다.

**마이너 버전을 올려도 해결되지 않습니다.** 8.0 계열 전체가 대상이라 8.0.46으로 가도
과금은 그대로입니다. **8.4로 올려야만 멈춥니다.**

### 어떻게 올리나 — 서비스 중단은 약 1분입니다

RDS Blue/Green 배포를 씁니다. 8.4 복제본을 미리 만들어 두고 검증한 뒤 이름만 맞바꾸는
방식이라, **쓰기가 막히는 시간이 약 1분**입니다. 접속 주소(엔드포인트)는 그대로 유지되므로
**앱 설정 변경이나 재배포는 필요 없습니다.**

### Q1. Connector/J 실제 해석 버전을 알려 주세요

`build.gradle`에 버전이 명시돼 있지 않고 Spring Boot BOM이 정하고 있어(`runtimeOnly
'com.mysql:mysql-connector-j'`), 저희 쪽에서 확정할 수 없었습니다. gradle 캐시에는
`8.3.0`과 `9.5.0`이 함께 남아 있어 어느 쪽인지 판단이 안 됩니다.

```bash
./gradlew :groble-api:groble-api-server:dependencies --configuration runtimeClasspath | grep mysql-connector-j
```

| 결과 | 조치 |
|---|---|
| **9.x** | 조치 불필요. 그대로 진행합니다 |
| **8.4.x** | 조치 불필요 |
| **8.3.0 이하** | ⚠️ **8.4 정식 출시 이전 드라이버**라 8.4 서버 조합이 공식 검증 범위 밖입니다. 올려 주시길 요청드립니다 |

### Q2. 직접 작성한 SQL 확인 — 범위를 좁혀 두었습니다

MySQL 8.4에서는 예약어가 늘고 일부 문법이 사라집니다. JPA가 자동 생성하는 쿼리는
드라이버가 알아서 처리하지만, **직접 쓴 SQL은 사람이 봐야 합니다.**

**인프라가 먼저 훑어본 것 — 여기는 문제 없었습니다.**

| 확인 대상 | 결과 |
|---|---|
| `@Query(nativeQuery = true)` **7건** (파일 4개) | ✅ 예약어로 쓰인 식별자 없음 |
| `ON DUPLICATE KEY UPDATE`의 구형 `VALUES()` 함수 | ✅ 저장소 전체에서 사용처 없음 (명명 파라미터 방식) |
| `utf8mb3` 문자셋 | ✅ 운영 DB 테이블·컬럼 모두 해당 없음 |
| MyISAM 테이블 | ✅ 106개 테이블 전부 InnoDB |

**봐 주셔야 하는 남은 범위 — `JdbcTemplate` / `createNativeQuery` 로 쓴 SQL입니다.**
운영 코드 기준 **9개 파일 40군데**입니다.

| 건수 | 파일 |
|---:|---|
| 11 | `persistence/dashboard/ReferrerTrackingQueryRepositoryImpl.java` |
| 7 | `persistence/settlement/SettlementCustomRepositoryImpl.java` |
| 6 | `persistence/user/AdminSellerRetentionRepositoryImpl.java` |
| 5 | `persistence/membership/MembershipTrialPromotionRepositoryImpl.java` |
| 4 | `persistence/purchase/AdminTradingStatsRepositoryImpl.java` |
| 2 | `persistence/activation/AdminActivationFunnelRepositoryImpl.java` |
| 2 | `persistence/membership/AdminFeatureUsageRepositoryImpl.java` |
| 2 | `groble-security/.../HardenedOAuth2AuthorizationService.java` |
| 1 | `persistence/membership/MembershipCustomRepositoryImpl.java` |

**무엇을 보면 되나 — 두 가지만 보시면 됩니다.**

1. **백틱 없이 쓴 식별자** 중 새로 예약어가 된 단어가 있는가
   (테이블·컬럼·별칭 이름을 백틱으로 감쌌다면 안전합니다)
2. **8.4에서 사라진 문법**을 쓰고 있는가 — 특히 복제·바이너리로그 관련 구문
   (`SLAVE` 계열 명령은 8.4에서 제거되고 `REPLICA` 로 바뀌었습니다)

> **더 확실한 방법이 있다면 그쪽이 낫습니다.** 저희가 그린(8.4) 인스턴스를 만들고 나면
> 실제 8.4 서버에 직접 쿼리를 돌려 볼 수 있습니다. **"눈으로 보는 것보다 직접 돌려 보고
> 싶다"** 고 하시면 그린을 먼저 띄우고 접속 정보를 드리겠습니다. 말씀만 주세요.

#### 참고 — 테스트로는 잡히지 않습니다

`BaseIntegrationTest.java:45`의 Testcontainers가 `mysql:8.0`으로 고정돼 있어
**8.4 비호환이 CI를 통과합니다.** 다만 이걸 `mysql:8.4`로 바꿔도 완전한 검증은 아닙니다 —
테스트 설정이 `flyway.enabled: false` / `ddl-auto: create`라 **실제 마이그레이션 219건이
돌지 않고** Hibernate가 스키마를 새로 만들기 때문입니다. 통합테스트 클래스도 2개뿐입니다.

그래도 **한 줄 바꿔 돌려 보시면 손해는 없습니다.** 이건 요청이 아니라 참고입니다.

### Q3. 전환 중 약 1분간 쓰기가 막힙니다 — 앱이 견디나요?

전환 순간 DB가 쓰기를 잠시 차단합니다. 읽기는 대체로 유지되지만, **그 시점에 처리 중이던
결제 트랜잭션**이 걱정입니다.

인프라가 파악하고 있는 구조는 이렇습니다. 재고 예약(`stock:reserved:*`)과 결제 멱등키
(`checkout:idempotency:*`)가 **Redis에만 있고 DB에는 없습니다.** 그래서 전환 중에
**"Redis에는 예약이 잡혔는데 DB 기록은 실패한"** 상태가 생길 수 있다고 보고 있습니다.

**여쭙고 싶은 것:**

1. DB 커넥션이 1분간 끊겼다 돌아올 때 **HikariCP가 스스로 복구**합니까? 재시작이 필요합니까?
2. 그 사이 실패한 결제 요청은 **자동으로 정리**됩니까? (예약 롤백, 멱등키 만료 등)
   아니면 수동 대사가 필요합니까?
3. **점검 공지가 필요한 수준**이라고 보십니까? 아니면 저트래픽 시간대면 조용히 지나갈까요?

**전환 시각은 트래픽이 가장 적은 새벽 4~6시로 잡을 예정입니다.** 최근 2주 실측상 이 구간이
피크(오후 4시)의 3분의 1 수준입니다. 날짜는 아직 미정이며, 회신 주시는 내용에 따라
정하겠습니다.

## 3. 인프라가 이미 확인한 것 — 걱정 안 하셔도 되는 부분

혹시 신경 쓰실까 봐 먼저 확인해 둔 것들입니다.

| 항목 | 결과 |
|---|---|
| **DB 계정 인증 방식** | ✅ **문제 없음.** `groble_root`가 구형 인증 방식(`mysql_native_password`)을 쓰고 있지만, **AWS가 8.4에서도 이 방식을 켠 채 고정**해 두어 그대로 접속됩니다 |
| **접속 주소** | ✅ **바뀌지 않습니다.** 앱 설정 변경·재배포 불필요 |
| **데이터** | ✅ 전환 전 스냅샷이 남고, 구 인스턴스도 일주일간 보존합니다 |
| **스키마** | ✅ MyISAM·utf8mb3 없음 (위 Q2 표) |

> 인증 방식은 8.4에서 문제가 안 되지만, MySQL이 **다음 메이저 버전에서 제거**할 예정이라
> 언젠가는 옮겨야 합니다. **이번 업그레이드와 묶지 않고 별건으로 진행**하겠습니다.
> 같이 바꾸면 문제가 생겼을 때 원인을 가릴 수 없기 때문입니다.

## 4. 별건으로 뒤따를 요청 (지금 답 안 하셔도 됩니다)

미리 알려 드리는 것뿐입니다. 이번 회신에 포함하실 필요 없습니다.

1. **`/actuator/health`의 liveness / readiness 분리.** 현재 이 엔드포인트가 DB 상태까지
   묶어서 판정하기 때문에, DB가 잠깐 끊기면 **앱은 멀쩡한데 로드밸런서가 서버를 죽은 것으로
   보고 재시작**시킵니다. 이번 전환에서는 인프라 쪽 설정을 임시로 완화해 우회하지만,
   앞으로 서버가 교체될 때마다 같은 문제가 반복됩니다.
2. **개발 환경 MySQL도 8.4로 정렬.** 운영만 8.4가 되면 비호환이 개발·CI를 통과해
   **운영에서 처음 드러납니다.** 운영 전환이 끝난 뒤 요청드리겠습니다.
